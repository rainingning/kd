# Fortran 用户独立工作区与任务归档改造 — 研发计划

- 版本：v1.0
- 对应需求：`docs/用户独立工作区与任务归档改造需求说明书.md`
- 计划性质：现有系统专项重构计划
- 目标版本：用户固定工作区 + 单用户串行执行 + 全终态归档 + 程序版本同步

---

## 1. 计划目标

在保留现有注册认证、参数模板、任务队列、通知和管理后台主体能力的基础上，完成以下改造：

1. 将任务执行目录从“每任务独立目录”改为“每用户固定工作区”。
2. 新用户注册和管理员创建用户时自动复制：
   - `DCR_3D.exe`
   - `libiomp5md.dll`
3. 按 Fortran 程序硬编码规则准备：
   - `model_DC.dat`
   - `mesh/mesh.mphtxt`
   - `Forward_data/`
4. 改为在用户根目录中无参数启动 `DCR_3D.exe`。
5. 保留多个排队任务，通过 `staging/{task_id}` 隔离任务参数和输入。
6. 将同一用户运行并发固定为 1，不同用户继续受全局并发数控制并行执行。
7. 所有终态都归档参数、输入、完整结果目录、stdout、stderr 和任务元数据。
8. 将结果下载从 stdout 改为 `Forward_data` ZIP。
9. 增加程序模板版本、SHA-256、批量同步、延期同步、工作区自检和归档重试。
10. 清空旧任务历史，为已有用户初始化新工作区，并完成正式 DCR_3D.exe 验收。

## 2. 实施原则

### 2.1 先建立安全边界，再替换执行链路

实施顺序必须遵守：

```text
程序模板与配置
  → 数据模型与迁移
  → 工作区服务
  → 新版 Mock
  → staging 提交
  → 用户锁与调度器
  → runner 与归档
  → 下载/恢复/清理
  → 管理后台与程序同步
  → 旧数据切换
  → 正式程序验收
```

禁止在归档和用户互斥机制未完成时，先把 runner 改为共享用户工作区运行，否则会产生任务文件互相覆盖风险。

### 2.2 文件系统操作必须可恢复

以下操作统一采用临时文件或临时目录加原子重命名：

- exe/dll 同步；
- 参数文件覆盖；
- 输入文件覆盖；
- staging 文件写入；
- archive 目录生成；
- ZIP 缓存生成。

### 2.3 归档优先于终态

计算结束不等于任务最终完成。只有归档成功后，任务才能进入最终 `COMPLETED`、`FAILED` 或 `CANCELED`，并允许该用户下一任务覆盖工作区。

### 2.4 保持 Mock 与正式模式一致

新版 Mock 必须模拟正式程序行为：

- 无命令行参数；
- 从当前工作目录读取 `model_DC.dat`；
- 从 `mesh/mesh.mphtxt` 读取输入；
- 向 `Forward_data/` 写入一个或多个结果文件；
- 支持模拟耗时、非零退出和部分结果；
- stdout/stderr 仅作为日志。

只有这样，Mock 测试才能覆盖真实目录和归档链路。

## 3. 前置输入与启动条件

### 3.1 客户必须提供的物料

| 编号 | 物料 | 最晚到位阶段 | 阻塞影响 |
|---|---|---|---|
| I-01 | `DCR_3D.exe` | 正式联调前 | 无法完成真实程序验收 |
| I-02 | `libiomp5md.dll` | 正式联调前 | 无法完成真实程序验收 |
| I-03 | 正式程序版本号和 SHA-256 | 程序模板模块验收前 | 无法冻结模板清单 |
| I-04 | 正式 `model_DC.dat` 样例 | 参数序列化开发前 | 无法实现字节级正确的序列化器 |
| I-05 | 参数清单和文件格式规范 | 参数序列化开发前 | 仍只能使用占位参数 |
| I-06 | `mesh.mphtxt` 样例 | 正式联调前 | 无法验证输入兼容性 |
| I-07 | 可核对的 `Forward_data/` 预期结果 | 正式联调前 | 无法判断真实计算结果正确性 |
| I-08 | 退出码和典型失败说明 | runner 验收前 | 失败原因映射不完整 |
| I-09 | 典型任务资源数据 | 压测前 | 无法确定安全全局并发数 |

### 3.2 项目启动门槛

正式进入开发前完成：

- [ ] 当前代码建立 Git 基线提交和版本标签
- [ ] `.env`、exe、dll、storage 保持在忽略列表中
- [ ] PostgreSQL 开发库和测试库可用
- [ ] 现有 59 个测试在基线环境运行并保存结果
- [ ] 完整备份现有数据库和 storage
- [ ] 创建专项分支
- [ ] 冻结本文目录命名和状态机设计

## 5. 分阶段研发任务

## P0 — 基线、方案冻结与测试环境

- 目标：为重构建立可回滚起点。
- 内容：

- 产出：基线提交、版本标签、变更分支。
- 验收：可从标签恢复当前版本。
- 依赖：无。
- 估算：0.5 人日。

### R0.2 恢复完整自动化测试环境

- 目标：让现有 59 个测试先在重构前全部可执行。
- 内容：
  - 启动 PostgreSQL；
  - 创建 `fortran_platform_test`；
  - 固定测试数据库配置；
  - 运行并保存基线测试报告。
- 产出：测试环境说明、基线测试报告。
- 验收：59 个测试全部执行；现有失败项有明确基线记录。
- 依赖：R0.1。
- 估算：1 人日。

### R0.3 冻结详细设计

- 目标：把需求转为可编码的状态机和文件事务方案。
- 内容：
  - 确定 `archive_status` 与任务 `status` 的组合；
  - 确定用户执行锁实现；
  - 确定归档失败重试和人工解锁规则；
  - 确定程序模板 manifest 格式；
  - 确定 ZIP 缓存策略；
  - 评审数据库/文件系统一致性方案。
- 产出：详细设计说明、状态迁移图、时序图。
- 验收：后端、前端、测试、运维共同评审通过。
- 依赖：专项需求确认。
- 估算：2 人日。

### R0.4 新版 Mock 设计与实现

- 目标：在正式 exe 到位前验证真实目录行为。
- 内容：实现无参数 `mock_dcr3d.py`，读取固定文件并生成 `Forward_data`。
- 产出：新版 Mock、样例 model/mesh、命令行测试。
- 验收：在任意符合目录规范的用户工作区直接启动 Mock，可生成多文件结果并模拟失败、超时。
- 依赖：R0.3。
- 估算：1.5 人日。

**P0 阶段出口：** 方案冻结、测试可运行、新版 Mock 可模拟正式程序。

- 估算：1.5 人日。

### R1.2 ORM 与 Schema 改造

## P2 — 程序模板与用户工作区

### R2.1 程序模板服务

- 目标：统一管理 exe/dll 版本和完整性。
- 内容：

  - 校验文件名、版本和 SHA-256；

- 产出：`program_template.py`、单元测试。
- 验收：缺文件、错误 hash、错误 manifest 均被拒绝；正确模板返回稳定版本信息。
- 依赖：R1.1。
- 估算：2 人日。

### R2.2 用户工作区服务

- 目标：统一创建、检查和修复用户目录。
- 内容：
  - 创建 mesh、Forward_data、staging、archives；
  - 复制 exe/dll；
  - 原子替换和 SHA-256 复核；
  - 工作区自检；
  - 失败补偿清理。
- 产出：`workspace.py`、工作区测试。
- 验收：初始化成功目录完全符合需求；任一步骤失败不留下“数据库成功、目录失败”的半成品。
- 依赖：R2.1、R1.2。
- 估算：3 人日。

### R2.3 接入注册和管理员创建用户

- 目标：所有用户创建方式统一初始化工作区。
- 内容：
  - 开放注册接入；
  - 管理员创建用户接入；
  - 用户删除接入安全目录删除；
  - 增加审计和错误响应。
- 产出：路由和服务变更、回归测试。
- 验收：两种创建方式结果一致；模板异常时创建失败且不发成功提示。
- 依赖：R2.2。
- 估算：2 人日。

### R2.4 已有用户初始化脚本

- 目标：上线时为已有用户批量建立新工作区。
- 内容：
  - dry-run；
  - 用户级执行结果；
  - 幂等处理；
  - 失败重试；
  - 校验汇总。
- 产出：`init_user_workspaces.py`、报告格式。
- 验收：重复执行不会破坏已初始化用户；失败用户可单独重试。
- 依赖：R2.2。
- 估算：2 人日。

**P2 阶段出口：** 新老用户均可获得可校验的独立程序工作区。

- 验收：并发协程和并发调度周期只能有一个操作获得同一用户锁。
- 依赖：R0.3、R1.2。

### R4.2 调度器改造

- 产出：dispatcher 改造、并发集成测试。
- 验收：同用户严格串行，不同用户可并行，归档期间不启动下一任务。

- 估算：3 人日。

### R4.3 工作区准备服务

### R5.2 所有终态接入归档

- 目标：消除未归档终态。

## 10. 发布与切换计划

### 10.1 发布前检查

- [ ] 正式程序模板校验通过
- [ ] 数据库和 storage 完整备份
- [ ] 迁移和回滚演练通过
- [ ] 没有运行中任务
- [ ] 全部自动化测试通过
- [ ] 前端生产构建通过
- [ ] 正式程序 UAT 通过
- [ ] 磁盘容量满足工作区、归档和 ZIP 峰值
- [ ] 发布窗口和回滚负责人已确认

### 10.2 切换步骤

1. 停止新任务提交；
2. 等待运行任务完成，或按审批终止并备份；
3. 停止后端服务；
4. 备份 PostgreSQL 和 storage；
5. 部署新代码和前端；
6. 执行 Alembic migration；
7. dry-run 旧历史清理；
8. 执行旧任务和通知清理；
9. 清理旧任务目录；
10. 初始化全部已有用户工作区；
11. 执行全用户工作区自检；
12. 启动后端；
13. 管理员检查模板、同步和资源状态；
14. 执行一个正式冒烟任务；
15. 恢复用户提交入口；
16. 观察首批任务的归档、下载和清理日志。

### 10.3 回滚触发条件

出现以下任一情况立即停止放量并评估回滚：

- 大量用户工作区初始化失败；
- 正式程序无法无参数启动；
- 同用户出现两个进程；
- 归档失败并有数据覆盖风险；
- 任务历史无法下载；
- 数据库 migration 异常；
- 磁盘增长超出安全阈值；
- 正式计算结果与客户基准不一致。

### 10.4 回滚方式

- 停止新后端和所有 DCR_3D.exe；
- 恢复发布前数据库备份；
- 恢复发布前 storage 备份；
- 切回基线代码和前端 dist；
- 验证旧版健康检查和任务查询；
- 经审批后恢复服务。

由于本次确认清空旧任务历史，只有同时恢复数据库和 storage 备份才能完整回滚，二者不可只恢复其一。

| 正式参数格式迟迟不到 | 无法完成 model_DC.dat 序列化和真实验收 | 先用新版 Mock，明确该项阻塞上线 |
| 固定工作区并发覆盖 | 参数、输入、结果串任务 | 数据库级用户锁，归档完成后才释放 |
| 归档失败后继续调度 | 历史结果永久丢失 | ARCHIVE_FAILED 阻塞用户并自动/人工重试 |
| Windows 杀进程后文件仍被占用 | 归档或同步失败 | 等待句柄释放、重试、必要时终止进程树 |
| 杀死父进程留下子进程 | 工作区仍被写入 | Windows Job Object 或进程树终止方案 |
| exe/dll 同步时运行 | 程序损坏或版本混用 | 同一用户锁、临时文件和原子替换 |
| Forward_data 很大 | 归档/ZIP 慢、磁盘不足 | 容量预检、后台 I/O、流式 ZIP、监控告警 |
| DB 与文件系统不一致 | 孤儿目录或错误索引 | 状态化文件事务、幂等操作、对账和重试 |
| 重启时固定工作区归属不清 | 错误归档到其他任务 | 数据库记录当前 workspace owner/task ID |
| 旧历史清理不可逆 | 客户数据丢失 | 强制备份、dry-run、双人确认、回滚演练 |
| 程序版本不可追溯 | 结果无法复现 | 每任务记录版本和 exe/dll SHA-256 |
| 前端仍把 stdout 当结果 | 用户下载错误内容 | API 契约测试和前端联动验收 |

## 12. 质量门禁

任何阶段进入下一里程碑前必须满足：

1. 代码评审完成；
2. 新增核心逻辑有自动化测试；
3. 现有回归测试无未解释失败；
4. 文件操作有失败路径和重试策略；
5. 路径均由平台生成，不接受用户输入服务端路径；
6. 关键管理员操作有审计；
7. 文档与实际 API、状态机和目录结构一致。

发布门禁：

- 自动化测试全部通过；
- 专项需求第 21 章全部 P0 验收项勾选；
- 正式 DCR_3D.exe 验收通过；
- 迁移和回滚演练通过；
- 客户确认正式参数和结果；
- 不存在会导致历史结果被覆盖的已知高风险缺陷。

## 14. 计划结论

本次改造不是简单修改进程启动参数，而是对任务文件生命周期和执行隔离模型的重构。研发工作的核心应放在：

1. 单用户工作区的互斥安全；
2. 排队任务 staging 隔离；
3. 所有终态的可靠归档；
4. 归档失败时的现场保护；
5. 程序版本和工作区同步；
6. 可演练的旧数据切换与回滚。

建议按照 P0～P10 顺序实施，在新版 Mock 全流程、故障恢复、迁移回滚和正式 DCR_3D.exe 验收全部通过后再上线。
